# プライベート共有とビジター

プライベートトンネルはサーバーに登録されますが、**公開ポートを占用しません**。別のエージェントで
あるビジターが自分のマシン上にリスナーを開き、認証され暗号化されたブリッジの上で、専用の共有
シークレットを使ってそれに到達します。内部のサービスを、公開インターネットではなく特定のノードに
公開したい場合に使います。

## 3 つの設定

提供側のエージェント、ビジターのエージェント、サーバーのそれぞれで 1 か所ずつ変更します。

### 提供側: トンネルをプライベートにする

```toml
[[tunnel]]
id = 1
mode = "tcp"
public = false                 # Omit port and bind
backend = [{ addr = "127.0.0.1:3000" }]

[[tunnel]]
id = 3
mode = "socks5"
public = false
[tunnel.target_policy]
allow = ["127.0.0.0/8", "::1", "10.0.0.0/8"]
```

TCP、UDP、ファイル、プロキシの入口に対応しています。**HTTP のドメインルーティングは HTTP の
リスナーに依存するためプライベートにはできません**。プライベートな TCP トンネルは任意の HTTP または
HTTPS のバックエンドに転送できます。明示的に `port = 0` を設定するのは、プライベートトンネルと
同等です。

### サーバー: 共有を宣言する

```toml
[share.office-web]
client = "office"              # Node name; for a server-local group use client = "local.<group-name>"
tunnel = 1                     # Stable tunnel ID
secret = "replace-this-shared-secret"
allow_clients = ["laptop"]     # An empty list allows every authenticated node that holds the share secret
direct = true                  # Allow P2P direct connection attempts
```

`secret` は 16–4096 バイトの長さで、共有ごとに別のものを使うべきです。`acl_mode`/`acl_rules` は
ビジターのブリッジ接続の送信元アドレスを確認します。共有シークレットだけでは匿名のクライアント
として接続するために使うことは**できません**。ビジターには通常のノードの識別情報と vkey が引き続き
必要です。サーバーは `client.NAME.enabled = false` によってノードを恒久的に無効化できます。

### ビジター: ローカルで待ち受ける

```toml
[[visitor]]
name = "office-web"
share = "office-web"
secret = "replace-this-shared-secret"
bind = "127.0.0.1:18080"
mode = "tcp"                   # tcp | udp | socks5
max_connections = 64
udp_idle = "60s"
```

| フィールド | 説明 |
| --- | --- |
| `name` | このエージェント内で一意である必要があります |
| `share` | サーバー側の共有名 |
| `mode` | `tcp`、`udp`、`socks5` のいずれか |
| `bind` | 固定のポートが必要です。起動時にバインドされ、ポートが使用中だと直ちに失敗します |
| `max_connections` | 1–4096、既定は 64。TCP 接続または UDP の送信元セッションの数です |
| `udp_idle` | 1 秒から 1 時間、既定は 60 秒。どちらかの方向の通信でセッションが延長されます |
| `acl_mode` / `acl_rules` | ビジターのリスナーへの接続の送信元アドレスを確認します |
| `target` | 動的な共有のみ。以下を参照してください |

すべてのビジターは、エージェントの接続数上限と 8 MiB の UDP キューイング予算も共有します。
ビジターが受け付けるのは、検証済みの証明書による TLS、WSS または QUIC だけです。

サーバーは、共有の ACL、ビジターの ACL、提供側のルーティング ACL を、**ビジターのブリッジの実際の
送信元アドレス**に対して適用します。LAN 上でビジターのポートに到達した生のアドレスが、信頼できる
送信元としてサーバーに転送されることはありません。

## 得られるもの

上記の設定では、ビジターのマシン上の `127.0.0.1:18080` に到達すると、office エージェント上の
`127.0.0.1:3000` に行き着きます。UDP の `127.0.0.1:15353` は office 上の `127.0.0.1:5353` に
対応します。

接続数と生のトラフィックは、ビジターと提供側の両方、およびそれらのユーザーとトンネルのリソースに
対してカウントされます。1 人のユーザーが両端を所有している場合は、両方の使用量が合算されます。
UDP の長さヘッダーと共有認証のメッセージは、業務のトラフィックとしてはカウントされません。

## 動的な対象

サーバーの共有で `dynamic = true` を設定すると、ビジターが対象を指定できます。

```toml
[[visitor]]
name = "office-proxy"
share = "office-proxy"
secret = "replace-this-shared-secret"
bind = "127.0.0.1:11080"
mode = "socks5"
target = "internal.example:443"
```

- 提供側は SOCKS5、HTTP フォワードプロキシ、または混合プロキシのトンネルである必要があります。
  UDP の対象には SOCKS5 または混合プロキシが必要です。
- 提供側の実際に解決された IP と対象ポリシーは引き続き確認されます。
- 動的な共有では、プロキシ入口に**個別のプロキシアカウントが存在しない**必要があります。
  アカウントが設定されている場合は拒否され、共有シークレットでプロキシ自身の認証を回避できない
  ようにしています。
- `target` がない場合、ビジターはサービスの入口全体に接続します。ファイルとプロキシのアカウントは
  引き続き通常どおり認証します。
- TCP のビジターは SOCKS の CONNECT または HTTP プロキシのセッションを通せます。SOCKS の
  UDP ASSOCIATE が返すサーバー側の UDP アドレスは、ビジター上でローカルのアドレスに自動的に
  マッピングされることはありません。

完全な SOCKS5 アクセスが必要な場合は、ビジターを `mode = "socks5"` にして、`target` を指定せずに
動的な共有を参照してください。SOCKS の CONNECT と UDP ASSOCIATE はビジター側で解決され、すべての
宛先が共有認証と提供側の対象ポリシーを通ります。`[visitor.auth.users]` はローカルの SOCKS
アカウントを設定するもので、アカウントが存在する場合、ビジターは匿名認証にダウングレードしません。
`max_connections` は SOCKS の制御接続と UDP の対象の関連を合わせてカウントするため、UDP を使う
場合は少なくとも 2 に設定してください。

## 管理と実行時

- 管理画面の「共有アクセス」ページで共有を作成、編集、削除できます。シークレットは既定で伏せられ、
  編集中にフィールドを空のままにすると現在の値が保持されます。
- 運用者（operator）が管理できるのは、自分が所有するユーザーの提供側の共有だけです。読み取り専用の
  アカウントは変更できません。
- API は `/api/shares` と `/api/shares/NAME` です。書き込みでは設定のバージョンと冪等性の
  リクエストキーを維持します。
- ブリッジが切断された後もローカルのリスナーは保持され、既存のセッションは完了し、新しい
  リクエストは再接続後に再開されます。
- 共有への変更は通常のデーモンのリロードを通じて反映され、既存の接続は切断されます。
- この経路はサーバーのリレーを通ります。直接リンクについては
  [P2P 直接接続とリレーへのフォールバック](p2p.md) を参照してください。

## 確認チェックリスト

1. サーバーの `--check` と両方のエージェントの `--check` が成功します。
2. ビジターの `127.0.0.1:18080` が提供側の `127.0.0.1:3000` の内容を返します。
3. 誤った `secret` を使ったビジター接続が拒否されます。
4. `allow_clients` の外側にあるノードが拒否されます。
5. サーバーに新しい公開リスナーが増えていないこと（`ss -ltnp` と比較して確認）。
