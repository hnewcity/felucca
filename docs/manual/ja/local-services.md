# サーバー上のローカルな対象と入れ子ルート

`[local.<name>]` を使うと、サーバー自身がエージェントもブリッジの資格情報もなしにサービスを提供
できます。ローカルトンネルのバックエンドは、別の登録済みトンネル（エージェント上のトンネルも
含む）に入るエイリアスも使えるため、入れ子のルートを構成できます。

## ローカルサービスのグループ

```toml
[user.office]
[user.office.limits]
max_connections = 100

[local.office]
user = "office"
dial_timeout = "10s"
[local.office.network]
local_ip = "127.0.0.1"
forward_local_ip = true

[[local.office.tunnel]]
id = 1
mode = "tcp"
port = 9001
bind = "127.0.0.1"
backend = [{ addr = "127.0.0.1:3000" }]
[local.office.tunnel.health]
type = "tcp"
interval = "10s"
timeout = "2s"
```

各グループでは `user`、`acl_mode`/`acl_rules`、`limits`、`network`、`dial_timeout` を設定でき、
エージェントと同じ TCP/UDP、HTTP/SNI、プロキシ、ファイル、負荷分散、プローブ、ACL の設定を
使えます。ローカルサービスだけを使う場合は、クライアントテーブルを省略できます。

ローカルグループはレジストリとトラフィックのスナップショットに `local.<name>` として記録され、
**この名前空間は外部エージェントの key_id として使えません**。ローカルグループにはブリッジが
ないため、上流プロキシの設定は拒否されます。`forward_local_ip = true` の場合だけ、バックエンドへの
接続にエグレス IP を使います。ファイルルート、証明書、バックエンドの設定は起動時に準備され、
待ち受けの衝突があるとそのサービスの起動は失敗します。

## バックエンドのエイリアス

| アドレス | 動作 |
| --- | --- |
| `tunnel://local.office/7` | 別の登録済みローカルトンネルのサービス入口に入ります |
| `tunnel://agent-1/7` | オンラインのエージェント上の登録済みトンネルに入ります |
| `file://agent-1/7` | 上記と同じですが、登録済みの対象が `file` モードであることを要求します。ディレクトリの境界、読み取り専用の状態、ファイル認証は保たれます |
| `bridge://tcp`、`tls`、`ws`、`wss` | 対応するブリッジ入口に入ります。エージェント側では相互認証が引き続き必要で、TLS はブリッジ証明書を使います |
| `bridge://http` | サーバーの HTTP 入口に入り、Host、サイト認証、権限の確認は引き続き実行されます |
| `bridge://web` | 管理用エンドポイントに接続し、認証方法は同じです |

トンネル番号は明示的で安定している必要があります。`user` を持つローカルグループが参照できるのは
同じユーザーの対象だけです。`user` を持たないグループはサーバーの運用者が管理し、ユーザーをまたいで
参照できます。`bridge` のエイリアスを使えるのは運用者のグループだけです。遠隔のエージェントと
動的プロキシのリクエストは、ネットワークの対象としてエイリアスを使えません。

エイリアスには追加の `backend.tls`、ネットワークのヘルスプローブ、入口側の対象 ACL は設定
できません。権限は各ホップの対象によって強制されます。HTTPS/SNI のエイリアスは TLS データを
直接通せ、対象のサイトがそれを終端するかパススルーします。UDP が入れ子にできるのは UDP だけ
であり、それ以外のモードはストリーム入口を使います。SOCKS5/HTTP プロキシの認証が省略される
ことはありません。

## ループ制御と課金

- すべてのホップが元の送信元 IP とポート、そしてルーティングの履歴を保持します。
- `(client, id)` の繰り返し、または**16 ホップ**を超える場合は直ちに拒否されます。
- HTTP の接続プールも履歴で分離されるため、再利用された接続がループの確認を回避することは
  ありません。
- 実際に通過したすべてのトンネルは、それぞれ独自の接続許容量を持ち、トラフィックを記録します。
  同じユーザーまたはグループが複数のホップを通過する場合、集約クォータもホップごとに請求されます。
- UDP の課金はメッセージのペイロードを対象とし、内部の長さフレームは含みません。

## よくある構成

| シナリオ | 方法 |
| --- | --- |
| サーバーホスト自身のサービスも公開する | `[local.ops]` + `[[local.ops.tunnel]]` |
| 内部サービスの前に TLS 終端を置く | `tls_mode = "offload"` を指定したローカルグループ内の HTTP トンネル |
| 内部サービスの上にもう一つ入口を重ねる（サイト認証など） | 外側のローカルグループで、バックエンドを `tunnel://agent-1/7` と書きます |
| 内部サービスから管理用エンドポイントの認証を再利用する | バックエンドを `bridge://web` と書きます |
