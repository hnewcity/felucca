# P2P 直接接続とリレーへのフォールバック

両端が NAT の背後にある場合、Felucca は UDP ホールパンチングによって QUIC の直接リンクを試み、
失敗した場合はサーバーのリレーにフォールバックできます。アプリケーションのデータはサーバーを
経由しません。主接続は引き続き制御と課金を担います。サーバー、提供側のエージェント、ビジターの
エージェントは同時にアップグレードする必要があります。

## サーバー: 観測用のポート

```toml
[bridge]
bind = "0.0.0.0:14028"

[p2p]
bind = "0.0.0.0:8025"        # Listen on this host
advertise = "203.0.113.10:8025"   # External UDP address both ends can reach, without a scheme
timeout = "5s"
max_pending = 128
```

| フィールド | デフォルト | 制約 |
| --- | --- | --- |
| `bind` | — | ローカルの待ち受けアドレス |
| `advertise` | — | 外部から到達できる UDP アドレス。URL スキームは**付けません** |
| `timeout` | `5s` | 500ms–10s |
| `max_pending` | `128` | 1–4096 |

`advertise` は KCP、QUIC、HTTP/3 が使う UDP ポートと重複してはいけません。設定内の `127.0.0.1`
が使えるのは、すべてのプロセスが同じホストで動くデモだけです。ネットワークをまたいで使う場合は、
サーバーの公開ドメイン名とポートに変更してください。

## 提供側: 直接接続を許可する

```toml
# provider agent
[p2p]
enabled = true
max_sessions = 64        # Default 64, maximum 1024
bind_ip = "192.0.2.10"   # Optional; fixes the local UDP IP

[[tunnel]]
id = 1
mode = "tcp"
public = false
backend = [{ addr = "127.0.0.1:3000" }]
```

```toml
# server: a share must enable direct explicitly
[share.office-web]
client = "office"
tunnel = 1
secret = "replace-this-shared-secret"
allow_clients = ["laptop"]
direct = true
```

サーバー、ローカルの提供側、共有のそれぞれで**明示的に有効にする**必要があります
（サーバーの `[p2p]`、提供側の `[p2p] enabled = true`、共有の `direct = true`）。両端の
主接続は、検証済みの証明書による TLS、WSS または QUIC を使う必要があります。`bind_ip` を
省略した場合はエージェントのエグレス IP の設定が使われます。これはバックエンドへのダイヤルに
使うエグレスは変更しません。

## ビジター: 接続の優先順位

```toml
# visitor agent
[[visitor]]
name = "office-web"
share = "office-web"
secret = "replace-this-shared-secret"
bind = "127.0.0.1:18080"
mode = "tcp"
connection = "prefer_direct"    # relay | prefer_direct | direct
```

| `connection` | 動作 |
| --- | --- |
| `relay` | 既定。既存のリレーを使います |
| `prefer_direct` | まず直接接続を試み、直接リンクを確立できず、かつアプリケーションデータをまだ送信していない場合はリレーにフォールバックします |
| `direct` | 直接接続のみを受け付けます。直接接続が利用できない場合はローカルの接続を閉じます |

## リンクの確立手順

1. 主接続でまずノードと共有シークレットの認証が完了します。サーバーはビジターの識別情報、
   送信元 ACL、両側の接続クォータを確認します。
2. サーバーはトンネル、送信元、対象、UDP の種別、符号化のオプション、PROXY の情報に紐づいた
   **使い捨てのチケット**を発行します。提供側のノードキーは渡しません。
3. 両端は異なるチケットキーを使って観測された UDP アドレスを探り、サーバーは短命で送信元に
   束縛された Cookie で戻り経路を確認し、有効なプローブの回数、チケットの枚数とその有効期間を
   制限します。未知のチケットには応答しません。
4. 提供側は観測に使ったものと同じ UDP ソケットを保持し、ビジターが観測したエンドポイントへ
   ホールパンチのパケットを送ります。
5. ビジターは QUIC TLS 1.3 で直接接続し、提供側の一時的な証明書のフィンガープリントを固定して
   から、束縛されたチケットと 2 つのノンスによる双方向の HMAC を完了します。
6. バックエンドの選択、健全性の状態、対象 ACL、ファイル認証、ディレクトリ機能のハンドルは、
   元のサービスエンジンを引き続き使います。

ホールパンチングが失敗した場合は、まず提供側の試行と両側のクォータが解放され、そのあとで初めて
リレー接続が許可されます。転送が始まった後の切断でアプリケーションデータが**再送されることは
ありません**。主接続の切断、無効化されたノード、クォータの枯渇、サービスの停止は、関連する
直接リンクを閉じます。

## 課金と制限

- アプリケーションのデータは両端の間を QUIC で流れ、サーバーのデータリレーは通りません。
- 提供側は方向ごとに、課金を待つデータブロックを最大 1 つだけ保持します（TCP ブロックは
  16 KiB 以下、UDP は 65507 バイト以下）。
- サーバーは送信前に両側のトラフィックとレートの範囲を確認して予約し、送信後に実際のバイト数を
  コミットします。シーケンス番号の重複、認可の重なり、クォータ超過のコミットは拒否されます。
- カウントの対象は**デコード後のアプリケーションのバイト数**で、プローブ、TLS、圧縮の
  オーバーヘッド、UDP のフレームヘッダー、TCP の PROXY ヘッダーは含みません。
- 直接接続の課金は、認証済みの提供側からの報告に依存します。サーバーは直接のペイロードを自分で
  観測できません。最終報告の前に提供側がクラッシュしたり制御接続が切断したりすると、送信済みだが
  未コミットのブロックが永続化されたカウントに記録されないことがあります。通常の停止では確認
  メッセージを通じて排出します。
- ブロックごとのクォータ要求は主接続の RTT への依存を増やすため、これをサーバーから切り離された
  無期限のオフライン直接リンクと説明する**べきではありません**。

## 対応するサービス

プライベートとパブリックの TCP、UDP、制限付きファイルサービスに対応し、動的な共有上では
SOCKS と HTTP フォワードプロキシの対象にも対応します。サイトの HTTP/SNI 入口、サーバー上の
ローカルと入れ子のルート、個別のプロキシアカウントを必要とする対象は、元の入口を迂回しません。
`prefer_direct` は元のリレーを使い、`direct` は拒否します。PROXY ヘッダーを有効にした UDP
バックエンドはリレーを使います。TCP の PROXY ヘッダーは提供側がバックエンドに書き込み、
その際にサーバーが認証した送信元アドレスを使います。

## デプロイの境界

宛先依存のマッピングが存在する場合、UDP が無効な場合など、これらに該当するときはリレーを使い
ます。実際の公開網の NAT の種類とキャリアのネットワークは、それが動くデプロイ環境で検証する
必要があります。ローカルの模擬を公開網の結果として扱わないでください。
