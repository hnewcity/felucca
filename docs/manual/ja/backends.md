# バックエンド、負荷分散、ヘルスチェック

このページではバックエンドの設定、5 つの負荷分散戦略、そしてヘルスチェックによってバックエンドが
追い出され復旧する仕組みを取り上げます。

## バックエンド

```toml
[[tunnel]]
mode = "tcp"
port = 9000
bind = "127.0.0.1"
balance = "round_robin"

[[tunnel.backend]]
addr = "127.0.0.1:3000"
weight = 2

[[tunnel.backend]]
addr = "backend.internal:3001"
weight = 1
tls = true
[tunnel.backend.trust]
mode = "pinned"
fingerprint = "<backend SHA-256>"
```

| フィールド | 説明 |
| --- | --- |
| `addr` | 必須。ホスト名または IP アドレスにポートを加えたもの |
| `weight` | `weighted` 戦略で使う正の整数の重み |
| `tls` | バックエンドへの TLS を有効にします。既定では WebPKI 検証を使い、SNI はアドレスのホスト名から取得します |
| `trust` | 自己署名のバックエンドには `mode = "pinned"` と `fingerprint` を使います |

`balance` は `[[tunnel]]` に属する項目で、`[[tunnel.backend]]` の後に書いてはいけません。
ヘルスチェックとデータ接続は同じ TLS 設定を使います。

## 負荷分散の戦略

| 戦略 | バックエンドの選び方 |
| --- | --- |
| `round_robin` | 健全なバックエンドを順番に巡回します |
| `weighted` | 正の整数の `weight` に応じて接続を振り分けます |
| `least_connections` | 現在開いている接続数が最も少ないバックエンドを選びます |
| `source_hash` | 元の利用者の IP アドレスから安定してバックエンドを選びます |
| `failover` | 設定順で最初の健全なバックエンドを選びます |

選択は**エージェント側**で行われます。接続数はバックエンド接続が切断またはキャンセルされた時点で
解放されます。重みが分散させるのはバイト数ではなく接続数です。

動作の詳細は以下のとおりです。

- すべてのバックエンドが unhealthy と判定されている場合でも 1 台には接続を試みます。これはプローブの
  設定ミスでトンネル全体が使えなくなる事態を避けるためです。
- 単一の接続失敗はエラーとして報告され、同じリクエスト内で別のバックエンドへ再試行することは
  **ありません**。
- `source_hash` は送信元 ACL または PROXY プロトコルで検証済みの元アドレスを使います。

## ヘルスチェック

```toml
[tunnel.health]
type = "http"                # "tcp" | "http"
path = "/healthz"
interval = "10s"
timeout = "2s"
failures_to_evict = 3
successes_to_restore = 2
expect_status = [200, 204]
```

| フィールド | 説明 |
| --- | --- |
| `type = "tcp"` | 接続が確立できることだけを確認します |
| `type = "http"` | 指定した `path` にリクエストし、既定では 2xx を成功と見なします |
| `expect_status` | 成功と見なすステータスコードを明示的に列挙します |
| `interval` | プローブの間隔 |
| `timeout` | 1 回のプローブのタイムアウト |
| `failures_to_evict` | 何回連続で失敗したらバックエンドを追い出すか |
| `successes_to_restore` | 何回連続で成功したらバックエンドを復旧させるか |

HTTP プローブはバックエンドのアドレスを Host として使います。連続した失敗はバックエンドを追い出し、
連続した成功は復旧させます。どちらもログに記録されます。

UDP トンネルと、接続先が動的に決まるプロキシ（socks5/httpproxy/mixedproxy）には、固定された
バックエンドがないため TCP や HTTP のバックエンドプローブを設定する**べきではありません**。接続先が
ディレクトリ機能のハンドルで決まる file モードも同様です。

## HTTP バックエンドのプール

HTTP トンネルのバックエンド接続プールは、クライアントセッション、トンネル、送信元 IP、対象、HTTP の
オリジンごとに分離されます。各オリジンではアイドル接続を最大 8 本、アイドルタイムアウトは 30 秒です。
外側のテーブルが保持するエントリは最大 256 件です。PROXY ヘッダーの送信を有効にしている場合、
プールは送信元ポートごとにも分離されます。複数の HTTP/2 リクエストが 1 本の接続を共有できます。

`response_timeout`（サーバー側の `[http]`）は、リクエストを送信してからバックエンドのレスポンス
ヘッダーを受け取るまでの時間を制限します。大きなファイルの低速なアップロードでは、それに応じて
値を大きくしてください。レスポンスボディは背圧の対象となり、全体をバッファリングすることは
ありません。
