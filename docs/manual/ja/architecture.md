# アーキテクチャと概念

このページでは Felucca の構成要素、トラフィックの流れ、そして後続のガイドすべてで使われる用語を
説明します。内部モジュールの責務の割り当てについては
[アーキテクチャ](../../architecture.md) に別途記載しています。

## デプロイの構成

```text
                    public network
 ┌──────────────────────────────────────────────────────┐
 │  felucca-server                                      │
 │  bridge   14028 (TCP/TLS/WS/WSS share one socket)    │
 │  quic     14028 (UDP, native QUIC streams)           │
 │  kcp      8025 (UDP)                                 │
 │  http     8080 / 8443 (+ http3 UDP)                  │
 │  admin    8088 (admin UI, optional)                  │
 └───────────────▲──────────────────────────────────────┘
                 │ agent dials out
        ┌─────────────────────┐
        │  felucca-agent      │    private network
        │  local service 3000 │
        └─────────────────────┘
```

エージェントは公開網上の `felucca-server` へ外向きに接続します。そのためプライベートネットワーク側に
公開 IP は不要で、ルーターのポートマッピングもファイアウォールの変更も不要です。ポート、ドメイン、
プロキシ、ファイルといった公開側の入口はすべてサーバーに属します。

## 2 つのプログラム

| プログラム | 役割 | 受信ポートが必要 |
| --- | --- | --- |
| `felucca-server` | エージェントの受け入れ、公開リスナーの保持、ルーティング、管理、計測 | 必要 |
| `felucca-agent` | プライベートネットワーク側から外向きに接続、ローカルリスナーの保持、バックエンドへのリクエスト送信 | 不要 |

両者は同じプロトコルバージョンを使う必要があります。現在のブリッジプロトコルバージョンは 10 であり、
**サーバーとエージェントは同時にアップグレードする必要があります**。プログラム名、バージョン、
プロトコル、ビルド対象は `--build-info` で表示できます。

```sh
target/release/felucca-server --build-info
target/release/felucca-agent --build-info
```

## 主要な概念

| 用語 | 意味 |
| --- | --- |
| **ブリッジ（bridge）** | サーバーとエージェントの間の長期間の接続。`bridge.bind` は TCP/TLS/WS/WSS が共有するアドレスで、既定値は `0.0.0.0:14028`。QUIC と KCP はそれぞれ専用の UDP ポートを使います |
| **identity（識別情報）** | エージェントは `key_id` + `vkey` で識別します。サーバー側には対応する `[client.<key_id>]` テーブルのエントリが必要です |
| **transport（通信方式）** | エージェント側で `tcp`、`tls`、`ws`、`wss`、`quic`、`kcp` から選択します。公開網では TLS/WSS/QUIC を推奨します |
| **trust（信頼）** | エージェントがサーバー証明書をどう検証するか。`webpki`（CA による検証）、`pinned`（SHA-256 フィンガープリントの固定）、`insecure`（診断専用） |
| **トンネル（tunnel）** | 1 つの公開入口からバックエンドの集合へのマッピング。`mode` が入口側のプロトコルを、`backend` が接続先を決めます |
| **バックエンド（backend）** | エージェントが実際に接続する対象で、`127.0.0.1:3000` のような形式で指定します |
| **リスナー（listener）** | サーバーがトンネル用に開くソケット。同じ `key_id` で再接続すると古いリスナーを置き換えます |
| **プライベート共有（share）** | 公開ポートを使わずに、登録済みのトンネルを名前を指定したビジターに開放します |
| **ビジター（visitor）** | 共有キーを保持する別のエージェントで、自分のマシン上にリスナーを開いてそのプライベート共有へアクセスします |
| **local（ローカル）** | エージェントを使わず、サーバー自身がサービスを提供する設定グループです |
| **mux** | TCP/TLS/WS/WSS/KCP の上で動作する、上限付きの多重化。ウィンドウのネゴシエーション、予算、背圧を提供します |
| **managed（集中管理）** | サーバーからエージェントへプッシュされるトンネル設定。エージェント側で `[remote]` を明示的に有効にする必要があります |

## 1 つのリクエストの流れ

TCP トンネルを例に取ります。

1. 利用者がサーバーの公開ポートへ接続します。
2. サーバーは送信元 ACL、クォータ、接続の許容可否を確認し、その接続を該当エージェントのブリッジ
   ストリームに割り当てます。
3. エージェントはリクエストを受け取り、負荷分散によって健全なバックエンドを選んで接続します。
4. mux ストリーム（またはネイティブな QUIC ストリーム）上で、どちらかが切断するまでデータが双方向に
   流れます。
5. サーバーはトラフィックを計測し、`[state]` または管理側が設定されていれば再起動をまたいで保持
   できます。

HTTP トンネルでは、ドメインとパスのルーティング、サイト認証という 2 つの手順が増えます。SOCKS5 トンネル
では、対象アドレスの名前解決と対象 ACL という手順がさらに 2 つ増えます。

## 内部モジュール

利用者としては通常これを気にする必要はありませんが、どの crate が何を担当するかの目安になります。

| crate | 役割 |
| --- | --- |
| `felucca-core` | 設定、識別情報、アクセスルール、計測の型。非同期ランタイムには依存しません |
| `felucca-mux` | 上限付きの多重化、ウィンドウ、背圧 |
| `felucca-proto` | ハンドシェイク、制御メッセージ、ビジターと直接接続のプロトコル |
| `felucca-transport` | TCP/TLS/WS/QUIC/KCP の接続への適合とエグレスネットワーク |
| `felucca-service` | 両側で共有するバックエンド接続、負荷分散、ヘルスチェック、制限付きファイル配信 |
| `felucca-server` | エージェントの受け入れ、入口側のルーティング、管理、実行時の状態 |
| `felucca-client` | エージェントの接続、再接続、構成の受信、ビジター |
| `felucca-cli` | 2 つのプログラム、起動時の設定、ログ、システムサービス、更新 |
