# Интеграция с внешними платформами

Секция `[node]` даёт внешней плоскости управления возможность управлять этим узлом: она может
вызывать API управления с отдельным токеном, либо узел может сам устанавливать исходящее соединение и
принимать запросы через обратный WebSocket. Изменения конфигурации также могут рассылаться как подписанные
обратные вызовы, а внешний трафик — импортироваться. Это собственный протокол управления Felucca; он
не совместим на уровне проводника с nps.

## Включение и области

```toml
[node]
id = "edge-a"
state_path = "state/node-events.json"
changes_window = 1024
usage_interval = "10s"

[node.platform.panel]
enabled = true
token = "replace-with-a-random-platform-token"
scope = "account"
user = "office"
mode = "direct"
```

| Поле | Значения и смысл |
| --- | --- |
| `scope` | `full` (полное управление; при этом нельзя задать `user`) или `account` (нужно задать существующего `user`, и можно управлять только клиентами и туннелями этого пользователя и читать состояние обратных вызовов этого арендатора) |
| `mode` | `direct` (токен может обращаться к публичному HTTP API управления), `reverse` (только обратный WS RPC; прямое использование этого токена против HTTP API управления возвращает 401) или `dual` (оба направления) |
| `enabled = false` | Обе точки входа прекращают работу, а существующие обратные соединения закрываются |

Токены должны быть не короче 16 байт, и каждая платформа должна использовать свой. Через HTTP
передавайте заголовок `Authorization: Bearer <token>`. Личности платформ отделены от локальных учётных
записей управления. Смена токена, его области или конфигурации соединения заменяет обратное
соединение; запросы на более старом соединении всё равно проверяются по текущей конфигурации.

Публичные адреса должны использовать HTTPS/WSS; HTTP/WS открытого текста разрешён только для
петлевых адресов в буквальном виде. WSS по умолчанию проверяет публичные центры сертификации, а
вместо этого можно использовать `trust = { mode = "pinned", fingerprint = "..." }`. Ненадёжное
доверие не разрешается. HTTP-обратные вызовы проверяют публичные центры сертификации и не следуют
редиректам.

## API прямого управления

Записи используют JSON, заголовок `If-Match: "<configuration revision>"` и уникальный `Idempotency-Key`.
Аутентификации по Cookie из браузера дополнительно требуют Origin и токен CSRF.

| Конечная точка | Поведение |
| --- | --- |
| `GET /api/node/status`, `/api/node/registration` | Идентификатор узла, идентификатор загрузки, сохранённая эпоха, версия, окно событий и видимое состояние подключения платформ |
| `GET /api/node/usage` | Состояние подключения клиентов, числа соединений и накопленные байты в обоих направлениях в пределах текущей области |
| `GET /api/node/changes?after=<epoch>:<sequence>&limit=100` | Сохраняемое окно изменений; значение `limit` находится в диапазоне 1–512 |
| `GET /api/node/callbacks?target=...&offset=0&limit=100` | Видимые очереди обратных вызовов, статистика доставки и записи постранично |
| `POST /api/node/callbacks/replay` | `{"ids":["delivery-uuid"]}`; снимает состояние ошибки и выполняет доставку повторно |
| `POST /api/node/callbacks/delete` | Удаляет только указанные видимые записи |
| `POST /api/node/kick` | `{"ids":["client-name"]}`; постоянно отключает и разрывает соединения клиентов, блокируя немедленное переподключение |
| `POST /api/node/sync` | Администратор заново активирует локальную сохранённую конфигурацию и очищает старое состояние времени выполнения, кэши и соединения |
| `POST /api/node/traffic` | Импортирует внешние приращения трафика, атомарно накапливая счётчики клиентов и владеющих пользователей |
| `GET/PUT/DELETE /api/platforms/<name>` | Управление платформами со стороны администратора |
| `GET/PUT/DELETE /api/webhooks/<name>` | Создание, изменение и удаление сохранённых вебхуков со стороны администратора |

Пакетные изменения конфигурации, полный экспорт и восстановление переиспользуют `/api/batch` и
`GET/PUT /api/config`. Синхронизация и отключение клиентов переиспользуют ту же транзакцию
конфигурации и ту же историю идемпотентности и увеличивают ревизию конфигурации. Действия с обратными
вызовами и импорт трафика не меняют ревизию конфигурации.

### Импорт трафика

Вы должны настроить `state.path`:

```json
{"items":[{"client":"office","inlet_bytes":1234,"export_bytes":5678}]}
```

Запрос несёт не более 128 элементов. Числа байтов должны быть целыми без знака, а несколько элементов
для одного клиента сначала объединяются. Ничего не записывается, пока не пройдут все проверки
разрешений, и если хотя бы одна запись выходит за пределы области или некорректна, весь пакет
отклоняется. Импортируйте трафик, который **ещё не измеряется плоскостью данных этого узла**; при
повторном импорте трафика, который узел уже измерил, он будет учтён дважды. Первый импорт обновляет
снимок до версии 2, которую более ранние сборки не могут прочитать.

## Обратный протокол WSS версии 1

После включения секции `[node]` запрос `GET /api/ws` принимает обновление до WebSocket по HTTP/1.1.
Собственные клиенты используют Bearer-токен. Браузер может использовать свой одноисходный Cookie
входа либо передать токен в подпротоколе
`["felucca-node-v1", "felucca-token.<unpadded base64url token>"]`. Сервер выбирает только
`felucca-node-v1` и не принимает аутентификацию через параметры URL. Он держит одновременно не более
16 прямых управляющих WebSocket.

Узел устанавливает исходящее соединение с `reverse_url`, и рукопожатие несёт Bearer-токен платформы и
подпротокол `felucca-node-v1`. Платформа должна выбрать этот подпротокол в своём ответе. Все
прикладные сообщения — текст JSON.

Узел сначала отправляет `hello` (node, boot, epoch, cursor, max_message, max_inflight, heartbeat_ms), а
затем платформа отправляет запросы:

```json
{"type":"request","id":"request-1","method":"GET","path":"/api/clients"}
```

```json
{"type":"request","id":"request-2","method":"POST","path":"/api/node/kick","headers":{"if-match":"\"3\"","idempotency-key":"kick-001"},"body":{"ids":["office"]}}
```

Ответы выглядят как
`{"type":"response","id":"request-1","status":200,"headers":{},"body":{...}}`. RPC переиспользует
аутентификацию, фильтрацию по арендаторам, CAS и поведение идемпотентности обычных обработчиков
управления. Можно передавать If-Match, Idempotency-Key, Accept и X-Felucca-CSRF, но нельзя
переопределить Host или Authorization. Вход, выход, SSE, выборка данных процессора и само обновление
до WebSocket не идут через RPC.

| Ограничение | Значение |
| --- | --- |
| Максимальный размер сообщения | 2 MiB |
| Число одновременных RPC на соединение | 2 |
| Число одновременных RPC в пределах узла | 16; избыточные запросы получают 429 |
| Повторяющийся идентификатор запроса в полёте | Соединение закрывается |
| Тайм-аут запроса | 504; повторяйте записи с тем же ключом идемпотентности |

Любая из сторон может отправить `{"type":"ping","nonce":1}`. Узел не перезаписывает неотвеченный ping
и закрывает соединение с переподключением, если подходящий pong не поступает дольше двух периодов
пульса, с задержкой от 1 до 30 секунд. Изменения конфигурации отправляют событие, а при отставании
подписки отправляется повторная синхронизация. После задания `usage_interval` узел периодически
отправляет сообщения об использовании, отфильтрованные по арендатору.

## Подписанные обратные вызовы

```toml
[node.webhook.events]
user = "office"

[node.webhook.events.delivery]
enabled = true
url = "https://panel.example/felucca/events"
signing_key = "replace-with-a-random-callback-signing-key"
timeout = "5s"
retry_max = 2
retry_backoff = "2s"
queue_max = 100
```

Заголовки запроса:

| Заголовок | Содержимое |
| --- | --- |
| `X-Felucca-Event-Id` | UUID доставки; он остаётся тем же при автоматических повторах и ручных повторных отправках |
| `X-Felucca-Timestamp` | Время Unix в миллисекундах для этого запроса |
| `X-Felucca-Signature` | `v1=`, за которым идёт HMAC-SHA256 в шестнадцатеричном виде в нижнем регистре |

Входные данные для подписи — это префикс UTF-8, соединённый напрямую с **сырыми байтами тела
запроса**:

```text
felucca-callback-v1\n<timestamp>\n<event-id>\n<body>
```

Получатель должен проверить подпись, проверить окно времени и убрать дубликаты по идентификатору
события. Успехом считается только код 2xx. Значение `retry_max` — это число дополнительных попыток
после первой доставки, а `retry_backoff` — фиксированный интервал. Доставка выполняется **не менее
одного раза**: если узел завершается до того, как успешное подтверждение записано на диск, перезапуск
может доставить тот же идентификатор снова. Обратные вызовы несут только метаданные изменений, а не
секреты конфигурации; после получения события получите нужные ресурсы с помощью API с текущими
разрешениями.

Значение `queue_max` ограничивает число сохранённых ожидающих и завершившихся ошибкой записей на
каждую цель. При превышении ограничения самые старые записи отбрасываются и учитываются как
отброшенные; значение `0` не сохраняет ни одной завершившейся ошибкой записи. Максимум в пределах
узла — 4096 записей. Отключение подписки сохраняет её существующую очередь. Удаление подписки или
смена URL получателя, ключа подписи, фильтров или шаблонов очищает старую очередь.

Окно событий записывает `node.started`, `config.changed`, `config.resync`, а также метаданные
создания, изменения и удаления клиентов, пользователей, централизованных туннелей и доменов. Запросы
фильтруются по арендатору. Истёкший, слишком далеко ушедший вперёд или не совпадающий по эпохе курсор
возвращает 410/reset_required; в этом случае сначала получите текущую конфигурацию, а затем
возобновите подписку с возвращённой позиции. Это ограниченное окно не хранит полные отличия
конфигурации и не является долгосрочным журналом аудита.

## Подписки реального времени и шаблоны

И прямые, и обратные WebSocket-соединения могут использовать эти пути, доступные **только через
WS RPC**: `GET /api/realtime/subscriptions`, а также `GET/PUT/DELETE /api/realtime/subscriptions/<name>`.
Подписки не изменяют сохранённую конфигурацию и не требуют If-Match. Каждое соединение допускает не
более 32 подписок размером не более 32 KiB каждая, и все они освобождаются при обрыве соединения.

```json
{
  "enabled": true,
  "selector": {"event_names":["client.updated"],"clients":["office"]},
  "content": {
    "body_template": {"message":"node {{event.client}} updated","event":"{{event}}"},
    "header_templates": {"x-event-name":"{{event.kind}}"}
  }
}
```

Шаблоны — это значения JSON, и они не выполняют скриптов. Они поддерживают `{{node}}`, `{{id}}`,
`{{epoch}}`, `{{event}}` и `{{event.kind}}`, ресурс, действие, пользователя, клиента, туннель, хост,
цель, последовательность, ревизию, timestamp_ms и трафик. Когда вся строка является единственным
заполнителем, первоначальный тип JSON сохраняется. Шаблоны не могут переопределить аутентификацию,
Cookie, заголовки длины и соединения HTTP, а также подписывающие заголовки `X-Felucca-*`.

## Уведомления о трафике

Параметры `traffic_report_interval` (100 мс–1 ч) и `traffic_report_step_bytes` включают уведомления об
импортированном трафике. Уведомление `client.traffic.reported` отправляется при первом импорте для
клиента, у которого есть квота трафика, а в дальнейшем при достижении порога по времени или по числу
байтов. Уведомление несёт признак `ephemeral: true`, поэтому оно не попадает в историю изменений,
очередь ошибок и повторы. Медленные получатели могут его пропустить; когда нужны полные данные,
читайте `/api/node/usage`.

## Контрольный список проверки

1. Запрос `GET /api/node/status` возвращает идентификатор узла, эпоху и состояние подключения
   платформы.
2. Обратное соединение WSS завершает цикл `hello` → `request` → `response`.
3. Получатель обратных вызовов успешно проверяет подписи, а повторная отправка того же
   идентификатора события не даёт дублирующего эффекта для бизнес-логики.
4. После команды `kick` клиент отключается и не может переподключиться немедленно.
5. После импорта трафика накопленные байты в `/api/node/usage` меняются сразу.
