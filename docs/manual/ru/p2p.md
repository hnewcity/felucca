# Прямое соединение P2P и откат на релей

Когда обе стороны находятся за NAT, Felucca может попытаться пробить NAT по UDP и установить
прямое соединение QUIC, а при неудаче откатиться на релей сервера. Данные приложения идут в обход
сервера; основное соединение по-прежнему несёт управление и учёт. Сервер, агент поставщика и агент
посетителя нужно обновлять вместе.

## Сервер: порт наблюдения

```toml
[bridge]
bind = "0.0.0.0:14028"

[p2p]
bind = "0.0.0.0:8025"        # Listen on this host
advertise = "203.0.113.10:8025"   # External UDP address both ends can reach, without a scheme
timeout = "5s"
max_pending = 128
```

| Поле         | По умолчанию | Ограничение                                             |
| ---          | ---          | ---                                                      |
| `bind`       | —            | Локальный адрес прослушивания                            |
| `advertise`  | —            | Внешне доступный UDP-адрес, **без** схемы URL            |
| `timeout`    | `5s`         | 500 мс–10 с                                              |
| `max_pending`| `128`        | 1–4096                                                   |

Адрес `advertise` не должен пересекаться с UDP-портами, которые используют KCP, QUIC или HTTP/3.
Значение `127.0.0.1` в конфигурации годится только для демонстраций, где все процессы запущены на
одном хосте; для работы между сетями замените его на публичное доменное имя сервера и порт.

## Поставщик: разрешить прямое соединение

```toml
# provider agent
[p2p]
enabled = true
max_sessions = 64        # Default 64, maximum 1024
bind_ip = "192.0.2.10"   # Optional; fixes the local UDP IP

[[tunnel]]
id = 1
mode = "tcp"
public = false
backend = [{ addr = "127.0.0.1:3000" }]
```

```toml
# server: a share must enable direct explicitly
[share.office-web]
client = "office"
tunnel = 1
secret = "replace-this-shared-secret"
allow_clients = ["laptop"]
direct = true
```

Сервер, локальный поставщик и общий доступ должны быть **явно включены** каждый (`[p2p]` сервера,
`[p2p] enabled = true` поставщика и `direct = true` общего доступа). Основное соединение обеих
сторон должно использовать TLS, WSS или QUIC с проверенным сертификатом. Когда `bind_ip` не указан,
используется конфигурация исходящего IP-адреса агента; она не меняет исходящий адрес, который
применяется для подключений к бэкендам.

## Посетитель: предпочтение соединения

```toml
# visitor agent
[[visitor]]
name = "office-web"
share = "office-web"
secret = "replace-this-shared-secret"
bind = "127.0.0.1:18080"
mode = "tcp"
connection = "prefer_direct"    # relay | prefer_direct | direct
```

| `connection`   | Поведение                                                                     |
| ---            | ---                                                                           |
| `relay`        | Значение по умолчанию; использует существующий релей                          |
| `prefer_direct`| Сначала пробует прямое соединение и откатывается на релей, когда прямое соединение установить не удалось и данные приложения ещё не отправлены |
| `direct`       | Принимает только прямое соединение; закрывает локальное соединение, когда прямая связь недоступна |

## Как устанавливается связь

1. Основное соединение сначала завершает аутентификацию узла и секрета общего доступа; сервер
   проверяет идентичность посетителя, ACL источника и квоты соединений обеих сторон.
2. Сервер выдаёт **одноразовый билет**, привязанный к туннелю, источнику, цели, типу UDP,
   параметрам кодирования и информации PROXY, и не передаёт ключ узла поставщика.
3. Обе стороны исследуют наблюдаемые UDP-адреса, используя разные ключи билета; сервер
   подтверждает обратный путь короткоживущим Cookie, привязанным к источнику, и ограничивает число
   корректных проб, число билетов и время их жизни; неизвестные билеты не получают ответа.
4. Поставщик сохраняет тот же UDP-сокет, который использовал для наблюдения, и отправляет пакеты
   пробивания NAT на конечную точку, которую наблюдает посетитель.
5. Посетитель подключается напрямую по QUIC TLS 1.3, закрепляя отпечаток временного сертификата
   поставщика, а затем выполняет двусторонний HMAC над привязанным билетом и двумя nonce.
6. Выбор бэкенда, состояние работоспособности, ACL целей, файловая аутентификация и дескрипторы
   возможностей каталогов по-прежнему переиспользуют первоначальный движок сервиса.

Если пробивание NAT не удалось, сначала освобождаются попытка поставщика и квоты обеих сторон, и
только затем разрешается соединение через релей. Обрыв после начала пересылки **не воспроизводит
данные приложения повторно**. Обрыв основного соединения, отключение узла, исчерпание квот или
остановка сервиса закрывают связанные прямые соединения.

## Учёт и ограничения

- Данные приложения идут по QUIC между двумя сторонами и не проходят через релей данных сервера.
- Поставщик хранит не более одного блока данных, ожидающего учёта, в каждом направлении (блоки TCP
  ≤ 16 KiB, UDP ≤ 65507 байт).
- Сервер проверяет и распределяет диапазоны трафика и скорости обеих сторон до отправки, а
  фиксирует фактические числа байтов после отправки; повторяющиеся номера последовательностей,
  перекрывающиеся авторизации и совершённые с превышением квоты операции отклоняются.
- При подсчёте используются **декодированные байты приложения**, без проб, TLS, накладных расходов
  на сжатие, заголовков кадров UDP и заголовков PROXY TCP.
- Прямой учёт опирается на отчёты аутентифицированного поставщика; сервер не может самостоятельно
  наблюдать полезную нагрузку прямого соединения. Если поставщик аварийно завершается или
  управляющее соединение обрывается до окончательного отчёта, последние отправленные, но не
  зафиксированные блоки могут не попасть в постоянные счётчики. Обычное завершение работы
  выгружается через сообщения подтверждения.
- Запросы квоты на каждый блок увеличивают зависимость от RTT основного соединения, поэтому это
  **не следует** описывать как неограниченное по времени прямое соединение в автономном режиме,
  отвязанное от сервера.

## Поддерживаемые сервисы

Поддерживаются приватные и публичные сервисы TCP, UDP, а также файловые сервисы с ограничениями,
наряду с целями прямого прокси SOCKS и HTTP в динамических общих доступах. Входы
HTTP/SNI веб-сайтов, локальные и вложенные маршруты сервера, а также цели, требующие отдельных
учётных записей прокси, не обходят первоначальную точку входа: `prefer_direct` использует
первоначальный релей, а `direct` отказывается. Бэкенды UDP с включёнными заголовками PROXY
используют релей; заголовки PROXY TCP записываются на бэкенд поставщиком, с использованием
проверенного сервером адреса источника.

## Границы развёртывания

Когда присутствует сопоставление, зависящее от адреса назначения, когда UDP отключён, и в
подобных случаях используется релей. Реальные публичные типы NAT и сети операторов всё равно нужно
проверять в той среде развёртывания, где они работают; не рассматривайте локальную имитацию как
результат работы в публичной сети.
