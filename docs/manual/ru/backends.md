# Бэкенды, балансировка и проверки работоспособности

На этой странице описана настройка бэкендов, пять стратегий балансировки и то, как проверки
работоспособности вытесняют бэкенды и возвращают их в работу.

## Бэкенды

```toml
[[tunnel]]
mode = "tcp"
port = 9000
bind = "127.0.0.1"
balance = "round_robin"

[[tunnel.backend]]
addr = "127.0.0.1:3000"
weight = 2

[[tunnel.backend]]
addr = "backend.internal:3001"
weight = 1
tls = true
[tunnel.backend.trust]
mode = "pinned"
fingerprint = "<backend SHA-256>"
```

| Поле | Описание |
| --- | --- |
| `addr` | Обязательно. Имя хоста или IP-адрес вместе с портом |
| `weight` | Положительный целый вес, используемый стратегией `weighted` |
| `tls` | Включает TLS до бэкенда. По умолчанию используется проверка WebPKI, а SNI берётся из имени хоста в адресе |
| `trust` | Для самоподписанных бэкендов используйте `mode = "pinned"` вместе с `fingerprint` |

Поле `balance` относится к `[[tunnel]]` и **не** должно указываться после
`[[tunnel.backend]]`. Проверки работоспособности и передача данных используют одну и ту же
конфигурацию TLS.

## Стратегии балансировки

| Стратегия | Как выбирается бэкенд |
| --- | --- |
| `round_robin` | По кругу перебирает здоровые бэкенды |
| `weighted` | Распределяет соединения по положительному целому `weight` |
| `least_connections` | Выбирает бэкенд с наименьшим числом открытых в данный момент соединений |
| `source_hash` | Стабильно выбирает бэкенд на основе первоначального IP-адреса пользователя |
| `failover` | Выбирает первый здоровый бэкенд в порядке следования в конфигурации |

Выбор выполняется на **стороне агента**. Счётчик освобождается, когда соединение с бэкендом
закрывается или отменяется. Веса распределяют именно число соединений, а не число байт.

Особенности поведения:

- Когда все бэкенды помечены как нездоровые, один из них всё равно используется для попытки
  подключения — чтобы неверно настроенная проба не вывела из строя весь туннель.
- Ошибка отдельного соединения возвращается вызывающей стороне и **не** приводит к повторной
  попытке с другим бэкендом в рамках того же запроса.
- Стратегия `source_hash` использует первоначальный адрес, проверенный ACL источника или
  протоколом PROXY.

## Проверки работоспособности

```toml
[tunnel.health]
type = "http"                # "tcp" | "http"
path = "/healthz"
interval = "10s"
timeout = "2s"
failures_to_evict = 3
successes_to_restore = 2
expect_status = [200, 204]
```

| Поле | Описание |
| --- | --- |
| `type = "tcp"` | Проверяет только то, что соединение может быть установлено |
| `type = "http"` | Запрашивает указанный `path`; по умолчанию принимает код 2xx |
| `expect_status` | Явно перечисляет допустимые коды состояния |
| `interval` | Интервал между пробами |
| `timeout` | Тайм-аут одной пробы |
| `failures_to_evict` | Сколько подряд идущих ошибок приводит к вытеснению бэкенда |
| `successes_to_restore` | Сколько подряд идущих успехов возвращает бэкенд в работу |

HTTP-проба использует адрес бэкенда в качестве значения Host. Последовательные ошибки
вытесняют бэкенд, а последовательные успехи возвращают его в работу; и то и другое
записывается в журнал.

UDP-туннелям и прокси с динамической целью (socks5/httpproxy/mixedproxy) не следует
назначать TCP- или HTTP-проверки бэкендов, потому что постоянного бэкенда у них нет. То же
относится к режиму file, где цель определяется описателем возможности доступа к каталогу.

## Пул соединений с HTTP-бэкендами

Пул соединений с бэкендами для HTTP-туннелей изолирован по сеансу клиента, туннелю,
IP-источнику, цели и HTTP-origin: на каждый origin допускается не более 8 простаивающих
соединений с тайм-аутом простоя 30 секунд, а внешняя таблица содержит не более 256 записей.
Когда включена отправка заголовка PROXY, пул дополнительно изолируется по порту источника.
Несколько запросов HTTP/2 могут делить одно соединение.

Поле `response_timeout` (таблица `[http]` сервера) ограничивает время от отправки запроса до
получения заголовков ответа бэкенда; при медленной загрузке больших файлов увеличьте его
соответствующим образом. Тела ответов используют обратное давление и не буферизуются целиком.
