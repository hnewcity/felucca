# Обратный прокси HTTP/HTTPS

На этой странице описана публикация внутренних HTTP-сервисов по домену и пути: маршрутизация,
перезапись заголовков и Host, редиректы, CORS, страницы ошибок, SNI, HTTP/2 и HTTP/3, совместное
использование портов и пересылаемые заголовки.

## Регистрация HTTP-маршрута

```toml
# Server side
[http]
bind = "0.0.0.0:8080"
tls_bind = "0.0.0.0:8443"

# Agent side
[[tunnel]]
mode = "http"
port = 8080                       # Must match http.bind or http.tls_bind
hosts = ["app.example.test", "*.example.test"]
balance = "round_robin"

[tunnel.options.http]
path = "/api/"
scheme = "any"
rewrite_prefix = "/v2/"
host = "backend.internal"

[[tunnel.backend]]
addr = "127.0.0.1:3000"
```

Туннель `http` не открывает отдельного слушателя; поле `port` определяет, к какому HTTP-слушателю
он подключается, и он доступен одновременно по HTTP и по HTTPS.

## Правила маршрутизации

```toml
[tunnel.options.http]
path = "/api/"
scheme = "any"        # any | http | https
```

Приоритет сопоставления: **точный домен, затем самый длинный префикс пути, затем точная схема**.
Доменные имена нечувствительны к регистру, а конечная точка нормализуется.

| Шаблон | Совпадения |
| --- | --- |
| Точный `app.example.test` | Только этот домен |
| Маска `*.example.test` | Совпадает с `a.example.test`, но **не** с `example.test` и не с `a.b.example.test` |

Повторные регистрации с одинаковыми доменом, путём и протоколом отклоняются. Запрос без
подходящего маршрута возвращает 404. Для одного домена можно зарегистрировать несколько путей и
назначить их разным туннелям.

## Параметры запросов и ответов

```toml
[tunnel.options.http]
rewrite_prefix = "/v2/"
host = "backend.internal"
cors = true
redirect = "https://new.example{path}"
force_https = true
request_headers = { x-source = "{remote_ip}", x-remove = "" }
response_headers = { x-proxy = "felucca" }
error_pages = { "502" = "<h1>Service unavailable</h1>" }
```

| Параметр | Поведение |
| --- | --- |
| `rewrite_prefix` | Перезаписывает префикс и сохраняет остаток пути и строку запроса |
| `host` | Перезаписывает заголовок Host, отправляемый на бэкенд |
| `request_headers` | Шаблоны заголовков; пустое значение удаляет этот заголовок |
| `response_headers` | Шаблоны заголовков ответа |
| `cors` | Возвращает `Access-Control-Allow-Origin: *`, а корректный предварительный запрос сразу получает 204. Предварительный запрос не требует учётной записи сайта, но фактический запрос по-прежнему требует аутентификации |
| `redirect` | Возвращает 307 |
| `force_https` | Возвращает 301, при этом в цели используется порт HTTPS-слушателя сервера (443 опускается). При регистрации должен существовать HTTPS-слушатель |
| `error_pages` | Заменяет тело ответа по коду состояния. Поддерживаются коды 400..599, не более 64 KiB на страницу |

Шаблоны поддерживают `{host}`, `{path}` (включая строку запроса), `{scheme}`, `{remote_ip}` и
`{remote_port}`. Значения берутся из первоначального запроса, а результат подстановки не
раскрывается повторно. Заголовки границ сообщения, такие как Content-Length и Transfer-Encoding, и
межузельные заголовки перезаписаны быть не могут; для Host есть отдельное поле.

Аутентификация сайта использует `Authorization: Basic`, а при ошибке возвращает 401. Проверенные
учётные данные не пересылаются на бэкенд.

## Режимы TLS

```toml
[tunnel.options.http]
tls_mode = "http"        # http | passthrough | offload
```

| Режим | Поведение |
| --- | --- |
| `http` | Режим по умолчанию. Обычный обратный прокси HTTPS |
| `passthrough` | Передаёт поток TLS как есть на бэкенд по SNI, и сертификат бэкенда показывается посетителям напрямую. В этом режиме `backend.tls` должен быть отключён |
| `offload` | Завершает TLS сертификатом SNI сервера, а затем отправляет на бэкенд произвольное содержимое TCP |

Режимы `passthrough` и `offload` занимают весь SNI и не могут сочетаться с параметрами пути или
заголовков HTTP, а также с аутентификацией сайта.

## Порты и протоколы

| Возможность | Описание |
| --- | --- |
| Точка входа | HTTP/1.1, HTTP/2, HTTP/3 |
| Бэкенд | HTTP/1.1, HTTP/2 (`backend_http2 = true`) |
| ALPN | TLS-входы поддерживают `h2` и `http/1.1`; входы открытого текста поддерживают заранее известный HTTP/2 |
| WebSocket | Автоматически преобразуется между тремя типами входов и двумя типами бэкендов. Вход HTTP/1.1 возвращает 101, а HTTP/2 или HTTP/3 использует расширенный CONNECT с `:protocol = websocket` |
| HTTP/3 | Требует `http.http3_bind`. Каждое QUIC-соединение допускает не более 128 двунаправленных потоков, с окном приёма 1 MiB на поток и 16 MiB на соединение. Оно закрывается после 30 секунд простоя, а заголовки запроса ограничены 32 KiB |

HTTP/3 — только протокол публичной точки входа; бэкенды по-прежнему используют HTTP/1.1 или
HTTP/2. Обычный HTTPS-ответ несёт заголовок `Alt-Svc`, и при отличии внешнего отображаемого порта
его можно переопределить через `response_headers`.

## Совместное использование портов

Поля `bridge.bind`, `http.bind` и `http.tls_bind` могут быть **одним и тем же** IP:port, и один
сокет демультиплексируется по характеристикам рукопожатия: напрямую подключённые агенты TLS/WSS
используют ALPN `felucca/9`, а веб-сайты — `h2`/`http/1.1` или отсутствие ALPN. Обычный `GET /ws`
остаётся запросом веб-сайта, и только корректное обновление до WebSocket входит в мост. Мост через
QUIC и HTTP/3 также могут делить один UDP-адрес с демультиплексированием по ALPN, при этом
сертификаты моста и сертификаты веб-сайтов выбираются и обновляются раздельно.

## Адреса клиентов

По умолчанию переданные клиентом заголовки `Forwarded`, `X-Forwarded-*` и `X-Real-IP` удаляются, а
затем `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host` и `X-Forwarded-Proto` устанавливаются по
прямому адресу источника или по источнику PROXY, проверенному через `http.proxy_accept`. Установите
`forwarded_headers = false`, чтобы отключить эту перезапись; это подходит для развёртываний, где вы
сами управляете всей цепочкой прокси. Межузельные заголовки и заголовки, перечисленные в
`Connection`, не передаются на следующий прыжок.
