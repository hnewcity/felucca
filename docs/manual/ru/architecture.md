# Архитектура и основные понятия

На этой странице объясняется, из каких частей состоит Felucca, как течёт трафик и какая
терминология используется во всех последующих руководствах. Распределение ответственности
между внутренними модулями описано отдельно в [Архитектура](../../architecture.md).

## Форма развёртывания

```text
                    public network
 ┌──────────────────────────────────────────────────────┐
 │  felucca-server                                      │
 │  bridge   14028 (TCP/TLS/WS/WSS share one socket)    │
 │  quic     14028 (UDP, native QUIC streams)           │
 │  kcp      8025 (UDP)                                 │
 │  http     8080 / 8443 (+ http3 UDP)                  │
 │  admin    8088 (admin UI, optional)                  │
 └───────────────▲──────────────────────────────────────┘
                 │ agent dials out
        ┌─────────────────────┐
        │  felucca-agent      │    private network
        │  local service 3000 │
        └─────────────────────┘
```

Агент сам устанавливает исходящее соединение с `felucca-server` в публичной сети, поэтому
частной сети не нужен ни публичный IP-адрес, ни сопоставление портов на маршрутизаторе, ни
изменения в межсетевом экране. Все публичные точки входа — порты, домены, прокси и файлы —
принадлежат серверу.

## Две программы

| Программа | Обязанности | Нужны входящие порты |
| --- | --- | --- |
| `felucca-server` | Принимает агентов, держит публичные слушатели, маршрутизирует, управляет и ведёт учёт трафика | Да |
| `felucca-agent` | Устанавливает исходящие соединения из частной сети, держит локальные слушатели, выполняет запросы к бэкендам | Нет |

Обе программы должны использовать одну и ту же версию протокола. Текущая версия протокола
моста — 10, и **сервер и агент нужно обновлять вместе**. Команда `--build-info` выводит имя
программы, версию, протокол и цель сборки:

```sh
target/release/felucca-server --build-info
target/release/felucca-agent --build-info
```

## Ключевые понятия

| Термин | Значение |
| --- | --- |
| **мост (bridge)** | Долгоживущее соединение между сервером и агентом. `bridge.bind` — адрес, общий для TCP/TLS/WS/WSS, по умолчанию `0.0.0.0:14028`; QUIC и KCP используют собственные UDP-порты |
| **идентичность (identity)** | Агент идентифицируется парой `key_id` + `vkey`; на сервере должна быть соответствующая запись таблицы `[client.<key_id>]` |
| **транспорт (transport)** | На стороне агента можно выбрать `tcp`, `tls`, `ws`, `wss`, `quic`, `kcp`. В публичной сети предпочтительны TLS/WSS/QUIC |
| **доверие (trust)** | Способ проверки агентом сертификата сервера: `webpki` (проверка через CA), `pinned` (фиксированный отпечаток SHA-256), `insecure` (только для диагностики) |
| **туннель (tunnel)** | Сопоставление одной публичной точки входа набору бэкендов. `mode` определяет протокол входа, `backend` — цель |
| **бэкенд (backend)** | Цель, к которой фактически подключается агент, в виде `127.0.0.1:3000` |
| **слушатель (listener)** | Сокет, который сервер открывает для туннеля. Переподключение с тем же `key_id` заменяет старый слушатель |
| **общий доступ (share)** | Сервер выдаёт зарегистрированный туннель именованному посетителю, не занимая публичный порт |
| **посетитель (visitor)** | Другой агент, владеющий ключом общего доступа; он открывает слушатель на своей машине, чтобы обращаться к этому общему доступу |
| **локальная группа (local)** | Группа конфигурации, в которой сервер предоставляет сервис сам, без агента |
| **mux** | Ограниченная по ресурсам мультиплексизация поверх TCP/TLS/WS/WSS/KCP с согласованием окна, бюджета и обратным давлением |
| **управляемая конфигурация (managed)** | Конфигурация туннеля, которую сервер рассылает агенту; агент должен явно включить `[remote]` |

## Жизнь запроса

Рассмотрим пример туннеля TCP:

1. Посетитель подключается к публичному порту на сервере.
2. Сервер проверяет ACL источника, квоту и разрешённое число соединений, после чего назначает
   соединение потоку моста соответствующего агента.
3. Агент получает запрос, выбирает балансировкой нагрузки здоровый бэкенд и устанавливает
   соединение.
4. Данные идут в обе стороны по потоку mux (или по собственному потоку QUIC), пока одна из
   сторон не закроет свою половину.
5. Сервер учитывает трафик и может сохранять его между перезапусками, если настроен `[state]`
   или управление через интерфейс администратора.

Туннель HTTP добавляет два шага: маршрутизацию по домену и пути, а также аутентификацию на
сайте. Туннель SOCKS5 добавляет ещё два: разрешение целевого адреса и ACL цели.

## Внутренние модули

Как пользователю вам обычно не нужно о них думать, но они объясняют, какой crate за что
отвечает:

| crate | Назначение |
| --- | --- |
| `felucca-core` | Конфигурация, идентичность, правила доступа, типы учёта трафика; не зависит от асинхронной среды выполнения |
| `felucca-mux` | Ограниченная мультиплексация, окна и обратное давление |
| `felucca-proto` | Рукопожатие, управляющие сообщения, протоколы посетителей и прямых соединений |
| `felucca-transport` | Адаптация соединений TCP/TLS/WS/QUIC/KCP и организация исходящей сети |
| `felucca-service` | Подключение к бэкендам, балансировка нагрузки, проверки работоспособности и ограниченная выдача файлов — общее для обеих сторон |
| `felucca-server` | Приём агентов, маршрутизация входного трафика, управление, состояние во время выполнения |
| `felucca-client` | Подключение агента, переподключения, приём конфигурации, посетители |
| `felucca-cli` | Две программы, конфигурация запуска, журналирование, системные сервисы, обновления |
