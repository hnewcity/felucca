# Сервисы, обновления, журналирование и мониторинг

На этой странице описана регистрация Felucca в диспетчере служб, безопасное обновление двоичных
файлов, ротация журналов, метрики и профилирование процессора.

## Установка как системного сервиса

Обе программы используют одинаковые подкоманды, а `--name` поддерживает несколько экземпляров:

```sh
felucca-server service --name office render --config /srv/felucca/server.toml
felucca-server service --name office --dry-run install --config /srv/felucca/server.toml
felucca-server service --name office install --config /srv/felucca/server.toml
felucca-server service --name office start
felucca-server service --name office status
felucca-server service --name office restart
felucca-server service --name office stop
felucca-server service --name office uninstall
```

| Платформа | Диспетчер | Область по умолчанию |
| --- | --- | --- |
| Linux | systemd | `user`; `--scope system` — уровень машины |
| macOS | launchd | `user`; `--scope system` — уровень машины |
| Windows | SCM | Только `system` |

Команда `render --platform systemd|launchd|windows` показывает определение для любой
поддерживаемой машины, не собирая команды через оболочку. Значение `--workdir` по умолчанию равно
каталогу, в котором лежит конфигурация, и относительные пути внутри конфигурации интерпретируются
относительно него. Параметр `--binary` выбирает, какая программа будет установлена. Дополнительные
аргументы службы указываются после `--`, например `-- --log-file /srv/felucca/agent.log`.

Установка **не перезаписывает** существующую службу с тем же именем и не запускает службу сразу. В
Linux она включает службу; в macOS служба инициализируется при следующем входе или запуске либо
когда вы явно выполняете `start`. Пользовательская служба systemd, которая должна присутствовать при
загрузке, требует от развёртывающего включить lingering, а пользовательская служба macOS зависит от
графического сеанса входа. Службы уровня машины выполняются от имени пользователя по умолчанию диспетчера служб, поэтому
измените пользователя запуска в соответствии со своим развёртыванием. В Windows служба
устанавливается от имени пользователя `NT AUTHORITY\LocalService`, и развёртывающий должен выдать
ему соответствующие разрешения на каталоги конфигурации, журналов, состояния и файлового каталога.

Деинсталляция сохраняет исполняемый файл, конфигурацию, журналы, сертификаты и состояние времени
выполнения.

Объём проверенного: в репозитории проверяются генерация определений, разбор plist в macOS,
изолированные обновления копий и реальное профилирование процессора. Также был собран и запущен в
OrbStack образ сервера Linux arm64 с проверкой входа в управление, мониторинга, TLS моста и
сохранности данных при пересоздании контейнера; см. запись о развёртывании.
Установка системных служб и диспетчеры служб Linux/Windows остаются непроверенными.

## Обновление двоичных файлов

Получите SHA-256 отдельного исполняемого файла из доверенного канала выпуска, затем проверьте или
замените работающую программу:

```sh
felucca-server update --source /downloads/felucca-server --sha256 <64-hex-digest> --check-only
felucca-server update --source /downloads/felucca-server --sha256 <64-hex-digest> --expect-version 0.1.0
felucca-agent  update --source https://releases.example/felucca-agent --sha256 <64-hex-digest>
```

Дайжест — это **основа доверия**, и он должен браться из доверенного манифеста выпуска. Входные
данные должны быть отдельным двоичным файлом, поэтому сначала распакуйте tar.gz/zip. Загрузки по
HTTPS проверяют сертификаты и не следуют редиректам; для частных загрузок используйте
`--token-env VARIABLE_NAME`, а учётные данные никогда не записываются в журналы. Загрузки
ограничены 512 MiB и 5 минутами. Проверка `--version`, ограниченная 10 секундами, выполняется только
после совпадения дайджеста и проверяет тип сервера/агента и необязательную версию. При ошибках
временные файлы удаляются, а блокировка обновления предотвращает одновременную замену. Замена
сохраняет первоначальные права на файл.

После этого нужно явно выполнить `service ... restart`; уже работающие процессы продолжают
использовать старую версию. Обновление внутри контейнера не работает при файловой системе образа,
доступной только для чтения, — вместо этого замените образ.

Когда меняется версия протокола, сервер и агент нужно обновлять вместе. Скрипт сборки пакетов
фактически запускает `--build-info` и отказывается смешивать двоичные файлы с разными версиями
протокола или разными целевыми платформами.

## Журналирование

На стороне сервера:

```toml
[log]
level = "info"
file = "/data/felucca.log"
json = true

[log.rotation]
max_bytes = 10485760
max_files = 5
interval = "24h"
```

Вывод идёт и в файл, и в stderr. Ротация выполняется между завершёнными событиями, поэтому порог
размера допускает ещё одно событие. Архивы нумеруются от `.1` до `.5`, причём `.1` — самый новый.
Интервал `interval` отсчитывается от момента открытия текущего файла, а перезапуск начинает период
заново. Эксклюзивная блокировка не даёт нескольким процессам выполнять ротацию одного пути, а новые
файлы журналов и блокировок в Unix имеют права 0600.

**Изменение конфигурации журналирования сервера требует перезапуска; плоскость управления отклоняет
онлайновые изменения этих параметров.** Агент вместо этого использует аргументы командной строки; см.
[модуль felucca-agent](agent.md).

## Мониторинг

Запросы `GET /metrics` и `GET /api/metrics` возвращают текст Prometheus. Используйте Bearer-токен
учётной записи управления или корректный сеанс, потому что **анонимной конечной точки метрик нет**, а
метрики учитывают видимость пользователя учётной записи.

Они покрывают работоспособность сервисов, ревизию конфигурации, состояние подключения и включённости
узлов, числа соединений, накопленный трафик узлов, готовность туннелей и накопленный трафик
туннелей. Учёт трафика переиспользует существующий сохраняемый MeterStore, поэтому данные переживают
перезапуск сервера, если вы включили секцию `[state]`. Страница «Мониторинг» интерфейса управления
показывает загрузку процессора хоста, физическую память, ёмкость файловой системы и скорость сети в
виде интерактивных линейных графиков, без текста Prometheus и указаний по настройке. Образцы
поступают каждые пять секунд и хранятся в памяти в течение часа; перезапуски процесса очищают
историю. Выберите окно 5 минут, 15 минут или 1 час. Наведите курсор, щёлкните для закрепления или
используйте клавиши со стрелками, чтобы увидеть точное время выборки, часовой пояс и значения.
Потяните ползуок диапазона или используйте кнопки масштабирования и сброса, чтобы масштабировать все
четыре графика вместе; живые обновления сохраняют выбранное абсолютное окно времени. Карточки
показывают минимум, среднее по выборкам и максимум для видимых наблюдений, а легенда сети
переключает ряды приёма и отправки. Метрики хоста доступны только администратору; остальные роли
видят трафик и соединения по разрешённым им ресурсам. Структурированная конечная точка — это
`GET /api/monitor?window=900` (поддерживаемые окна: 300, 900, 3600 секунд).

## Профилирование процессора

После того как вы зададите `[admin] profiling = true`, администратор может вызвать
`POST /api/profile` с телом JSON `{"seconds":5}` или загрузить график пламени процессора со страницы
«Мониторинг». Поддерживаются Linux и macOS, остальные платформы отказываются включать эту
возможность. Каждый запуск занимает от 1 до 30 секунд на частоте 49 Гц, в процессе допускается
только одна задача за раз, а вывод ограничен 8 MiB. Отброшенный HTTP-запрос не освобождает
блокировку выборки досрочно, а остановка службы отменяет сбор выборок. Когда за период простоя
выборок нет, возвращается поясняющий SVG. Выпуски сохраняют символы функций для профилирования, но
отбрасывают отладочную информацию о строках; поиск на уровне строк требует сборки, созданной вами с
отладочной информацией.

## Docker

```sh
docker build --target server -t felucca-server:local .
docker build --target agent  -t felucca-agent:local .

docker run --rm -p 14028:14028 \
  --mount type=bind,src=/srv/felucca/config,dst=/etc/felucca,readonly \
  --mount type=bind,src=/srv/felucca/data,dst=/data \
  felucca-server:local
```

По умолчанию образы используют UID/GID 10001. Смонтируйте каталог конфигурации только для чтения и
разрешите образу запись в каталог данных. Откройте дополнительные TCP/UDP-порты, которые нужны вам в
конфигурации, явно и привязывайтесь к адресам, доступным изнутри контейнера. Мультиархитектурные
образы можно собирать с помощью Buildx, используя собственные цели из Dockerfile. Сигнал
`STOPSIGNAL` — SIGTERM, что соответствует пути завершения работы программы.

### Локальный OrbStack

Запустите OrbStack, затем выполните `sh scripts/run-orbstack.sh` из корня репозитория. Это собирает и
разворачивает только сервер, включая интерфейс управления. Хосту нужны Docker Compose, Python 3 и
OpenSSL. Откройте `http://127.0.0.1:8088` и войдите как `root`, используя случайный пароль из файла
`conf/orbstack/credentials.json`. Слушатель управления привязан только к петлевому адресу.

Учётные данные и постоянный сертификат моста находятся в каталоге `conf/orbstack/`, который
игнорируется Git. Конфигурация и снимки трафика находятся в томе `felucca_server-data`. Файл учётных
данных хранит первоначальный пароль; сохранённая конфигурация управления имеет приоритет над
начальным TOML. Повторный запуск скрипта собирает текущие исходники и обновляет контейнер, сохраняя
существующие учётные данные, сертификаты и данные.

Контейнер перезапускается вместе с движком Docker, если его не остановить вручную. Изначально
клиенты не настроены. Мост по TCP и QUIC использует порт 14028. Compose использует сетевую подсистему
хоста OrbStack, поэтому дополнительные порты туннелей не требуют отдельных отображений портов Docker.
Избегайте портов, которые уже заняты другими локальными программами.

```sh
docker --context orbstack compose -f compose.orbstack.yaml logs --tail 100 server
docker --context orbstack compose -f compose.orbstack.yaml restart server
docker --context orbstack compose -f compose.orbstack.yaml down
```

Команда `down` сохраняет том данных. Добавление `-v` удаляет сохранённые конфигурацию и данные
трафика.

## Сборка пакетов и CI

```sh
npm --prefix apps/admin ci
npm --prefix apps/admin run build
sh scripts/cargo-external.sh build --release --locked -p felucca-cli --bins
python3 scripts/package.py --output dist
```

Для сборки из исходников нужен Node.js 22.12+ (рекомендуется 24). Интерфейс управления на React +
Vite из каталога `apps/admin/` встраивается в двоичный файл сервера; для развёртывания Node.js не
требуется. Пересоберите интерфейс после его изменения: Cargo отклоняет отсутствующие или устаревшие
наборы файлов.

Артефакты содержат обе программы, примеры, документацию, манифест дайджестов по каждому двоичному
файлу и дайджест архива. Двоичные файлы, которые не могут работать на машине сборки, отклоняются по
умолчанию, а кроссплатформенная сборка в CI упаковывается на каждой целевой платформе. Рабочий
процесс GitHub выполняет проверки, тесты и архивацию для Linux amd64/arm64, macOS arm64 и Windows
amd64, а также отдельно проверяет минимальную версию Rust 1.88 и сборку Docker. Рабочий процесс
выгружает только артефакты заданий; он не создаёт выпуск GitHub и не публикует образы.

## Контрольный список проверки

```sh
felucca-server service --name office render --config conf/server.toml
felucca-server --config conf/server.toml --fingerprint
felucca-agent  --config conf/agent.toml  --check
```

Команда `--fingerprint` требует, чтобы конфигурация ссылалась на фиксированные PEM-файлы. Команда
`--check` не означает, что бэкенды, DNS, файлы сертификатов или публичные порты уже доступны.
