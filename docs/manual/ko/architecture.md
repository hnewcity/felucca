# 아키텍처와 개념

이 페이지에서는 Felucca를 구성하는 요소, 트래픽이 흐르는 방향, 이후 모든 가이드에서
사용하는 용어를 설명합니다. 내부 모듈 소유권은
[아키텍처](../../architecture.md)에 별도로 정리되어 있습니다.

## 배포 형태

```text
                    public network
 ┌──────────────────────────────────────────────────────┐
 │  felucca-server                                      │
 │  bridge   14028 (TCP/TLS/WS/WSS share one socket)    │
 │  quic     14028 (UDP, native QUIC streams)           │
 │  kcp      8025 (UDP)                                 │
 │  http     8080 / 8443 (+ http3 UDP)                  │
 │  admin    8088 (admin UI, optional)                  │
 └───────────────▲──────────────────────────────────────┘
                 │ agent dials out
        ┌─────────────────────┐
        │  felucca-agent      │    private network
        │  local service 3000 │
        └─────────────────────┘
```

에이전트가 공개 네트워크의 `felucca-server`로 바깥 방향 연결을 시도하므로, 사설
네트워크에는 공개 IP도, 라우터의 포트 매핑도, 방화벽 변경도 필요하지 않습니다. 모든 공개
진입점 — 포트, 도메인, 프록시, 파일 — 은 서버에 속합니다.

## 두 개의 프로그램

| 프로그램 | 역할 | 인바운드 포트 필요 |
| --- | --- | --- |
| `felucca-server` | 에이전트 수락, 공개 리스너 보유, 라우팅, 관리, 계량 | 예 |
| `felucca-agent` | 사설 네트워크에서 외부로 연결, 로컬 리스너 보유, 백엔드 요청 전송 | 아니요 |

두 프로그램은 같은 프로토콜 버전을 사용해야 합니다. 현재 브리지 프로토콜 버전은 10이며,
**서버와 에이전트를 함께 업그레이드해야 합니다**. 프로그램 이름, 버전, 프로토콜, 빌드
대상을 출력하려면 `--build-info`를 사용하세요.

```sh
target/release/felucca-server --build-info
target/release/felucca-agent --build-info
```

## 핵심 개념

| 용어 | 의미 |
| --- | --- |
| **브리지(bridge)** | 서버와 에이전트 사이의 장기 연결입니다. `bridge.bind`는 TCP/TLS/WS/WSS가 공유하는 주소이며 기본값은 `0.0.0.0:14028`입니다. QUIC과 KCP는 각자 별도의 UDP 포트를 사용합니다 |
| **신원(identity)** | 에이전트는 `key_id` + `vkey`로 식별되며, 서버에는 대응하는 `[client.<key_id>]` 테이블 항목이 있어야 합니다 |
| **전송(transport)** | 에이전트 쪽에서 `tcp`, `tls`, `ws`, `wss`, `quic`, `kcp` 중 선택할 수 있습니다. 공개 네트워크에서는 TLS/WSS/QUIC을 권장합니다 |
| **신뢰(trust)** | 에이전트가 서버 인증서를 검증하는 방식입니다. `webpki`(CA 검증), `pinned`(고정 SHA-256 지문), `insecure`(진단 전용) |
| **터널(tunnel)** | 공개 진입점 하나를 백엔드 집합에 연결하는 매핑입니다. `mode`가 진입 프로토콜을, `backend`가 대상을 결정합니다 |
| **백엔드(backend)** | 에이전트가 실제로 연결하는 대상으로, `127.0.0.1:3000` 같은 형태입니다 |
| **리스너(listener)** | 서버가 터널을 위해 여는 소켓입니다. 같은 `key_id`로 재연결하면 기존 리스너를 대체합니다 |
| **공유(share)** | 서버가 등록된 터널을 공개 포트 없이 이름 붙은 방문자에게 허용하는 것을 말합니다 |
| **방문자(visitor)** | 공유 키를 가진 다른 에이전트로, 자신의 머신에서 리스너를 열어 그 공유에 접근합니다 |
| **로컬(local)** | 에이전트 없이 서버가 직접 서비스를 제공하는 설정 묶음입니다 |
| **멀티플렉싱(mux)** | TCP/TLS/WS/WSS/KCP 위의 범위가 제한된 멀티플렉싱으로, 창 협상, 예산, 백프레셔를 제공합니다 |
| **관리(managed)** | 서버가 에이전트에 배포하는 터널 설정입니다. 에이전트가 `[remote]`를 명시적으로 활성화해야 합니다 |

## 요청의 생명주기

TCP 터널을 예로 들면 다음과 같습니다.

1. 방문자가 서버의 공개 포트에 연결합니다.
2. 서버가 출발지 ACL, 할당량, 연결 허용량을 검사한 뒤, 해당 연결을 일치하는 에이전트의
   브리지 스트림에 할당합니다.
3. 에이전트가 요청을 받아 로드 밸런싱으로 정상 백엔드를 고르고 연결합니다.
4. 데이터는 한쪽이 닫힐 때까지 mux 스트림(또는 네이티브 QUIC 스트림) 위에서 양방향으로
   흐릅니다.
5. 서버가 트래픽을 계량하며, `[state]`나 관리 쪽이 설정되어 있으면 재시작 후에도 이어서
   계량할 수 있습니다.

HTTP 터널은 두 단계가 추가됩니다. 도메인/경로 라우팅과 사이트 인증입니다. SOCKS5
터널은 두 단계가 더 추가됩니다. 대상 주소 조회와 대상 ACL 검사입니다.

## 내부 모듈

사용자라면 보통 이 내용을 신경 쓰지 않아도 되지만, 어떤 크레이트가 무엇을 담당하는지
보여줍니다.

| 크레이트 | 목적 |
| --- | --- |
| `felucca-core` | 설정, 신원, 접근 규칙, 계량 타입. 비동기 런타임에 의존하지 않습니다 |
| `felucca-mux` | 범위가 제한된 멀티플렉싱, 창, 백프레셔 |
| `felucca-proto` | 핸드셰이크, 제어 메시지, 방문자 및 직접 연결 프로토콜 |
| `felucca-transport` | TCP/TLS/WS/QUIC/KCP 연결 적응과 이그레스 네트워킹 |
| `felucca-service` | 양쪽이 공유하는 백엔드 연결, 로드 밸런싱, 헬스 체크, 제한된 파일 서빙 |
| `felucca-server` | 에이전트 수락, 인그레스 라우팅, 관리, 런타임 상태 |
| `felucca-client` | 에이전트 연결, 재연결, 설정 수신, 방문자 |
| `felucca-cli` | 두 개의 프로그램, 시작 설정, 로깅, 시스템 서비스, 업데이트 |
